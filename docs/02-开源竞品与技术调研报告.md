## 1. 调研范围与方法

### 1.1 调研目标

为"完整复刻 Beyond Compare（BC）功能"的新项目（文件/目录比较与合并工具）提供：

- 竞品的功能与架构盘点（它们如何分层、如何解耦 diff 引擎 / 文件访问 / UI / 会话管理）
- diff / 三向合并算法的原理、实现差异与可复用库
- UI 技术栈（Electron / Tauri / Qt / 纯 Native）的量化对比与推荐
- 文件系统与协议访问（本地/远程/压缩包）、大目录与 GB 级文件的性能方案素材

### 1.2 调研对象

| 类别 | 对象 |
|---|---|
| 全功能 GUI 竞品 | Meld、KDiff3、WinMerge、diffuse、P4Merge（闭源免费，仅功能参考） |
| 现代 diff 工具 | difftastic、git delta、VS Code 内置 diff / Monaco |
| 历史/终端工具 | tkdiff、xxdiff、kompare、vimdiff |
| 结构化数据 diff | jd（JSON diff/merge） |
| 算法与库 | Myers / patience / histogram / diff3、difflib、diff-match-patch、similar、imara-diff、jsdiff、go-diff、node-diff3 等 |

### 1.3 方法与数据来源

- **活跃度/star 数**：GitHub REST API 实时抓取（数据获取时间 **2026-11-13**）；Meld/KDiff3/kompare 的 canonical 仓库在 GNOME GitLab / KDE invent，star 数取自 GitHub 只读镜像，仅供量级参考。
- **架构事实**：直接读取各项目源码目录结构与关键文件（如 `meld/matchers/*`、`kdiff3/src/diff.cpp`、`WinMerge/Src/CompareEngines/*`），保证"模块划分 / 算法实现"部分有源码依据而非二手资料。
- **背景资料**：官方文档、Git 官方 diff 文档、VS Code 团队的算法说明、相关 HN/Reddit 讨论。

> 注：star 数为获取时点的快照；GPL 系项目的 star 普遍偏低（历史项目、托管在 GitLab/invent），不代表用户量。

## 2. 竞品逐个分析

### 2.1 Meld（GTK / Python）

| 项 | 内容 |
|---|---|
| 仓库 | https://gitlab.gnome.org/GNOME/meld （镜像 https://github.com/GNOME/meld ） |
| 技术栈 | Python 3 + GTK3/PyGObject（GTK4 移植中，3.23.1 为最后一个 GTK3 开发版）；文本编辑区基于 **GtkSourceView** |
| 许可证 | **GPL-2.0**（代码不可直接复用于闭源项目，行为可参考） |
| 活跃度 | GH 镜像 1,362 star；稳定版 3.22.2（2024-03），开发版 3.23.x（2025），3.24.x（2026）；维护者 Kai Willadsen 持续活跃；macOS 官方化打包进行中 |

**模块划分（源码 `meld/` 目录实测）**

| 子模块 | 文件 | 职责 |
|---|---|---|
| diff 引擎（纯 Python，与 UI 解耦） | `matchers/myers.py`、`matchers/diffutil.py`、`matchers/merge.py` | Myers 双向 diff；基于 difflib 扩展的多文件 diff 工具；三方合并状态机（含冲突分类） |
| 视图（每种比较类型一个类，均继承 `MeldDoc`） | `filediff.py`（2/3 向文本）、`dirdiff.py`（目录）、`imagediff.py`（图片，3.23+）、`vcview.py`（版本控制） | 面向对象的"文档"抽象，统一在 tab 中承载 |
| 版本控制适配层 | `vc/`（git、svn、hg、bzr、darcs 等 ~15 种，全部 subprocess 调用 CLI） | 极简适配器模式，新增 VCS 只需实现统一接口 |
| 文件系统访问 | GIO / GVfs（`Gio.File` 贯穿全代码） | 免费获得 sftp/ftp/afp 等已挂载远程协议 |
| 会话/配置 | `windowstate.py`、`recent.py`、GSettings | 窗口布局持久化 + 最近会话 |
| 任务调度 | `task.py`（LIFO 线程池 + 调度任务） | 后台扫描/IO 不阻塞 GTK 主循环 |

**diff 算法**：`matchers/myers.py` 为自研 Myers O(ND) 纯 Python 实现（含公共前缀/后缀二分裁剪），difflib 的 SequenceMatcher 作为辅助；行内高亮由"行级配对 + 词级再 diff"得出。

**目录比较**：`dirdiff.py` 关键实现——
- 异步枚举（GIO async enumerate）+ `_scan_in_progress` 计数控制并发扫描；
- **stat 缓存**：`CacheResult(stats, result)` 以 (size, mtime) 为 key 缓存"内容比较结果"，避免重复读文件；
- 内容比较用 **mmap（ACCESS_COPY）+ 哈希**；
- 对齐配对按相对路径逐层配对，支持仅大小写不同/Unicode 归一化提示。

**三向合并**：`matchers/merge.py`，基于两两 diff 结果合成三方块图，冲突分"冲突/一方修改/同时相同修改"等状态。

**语法高亮**：GtkSourceView（语言定义 XML 生态，LGPL）。

**性能处理**：stat 缓存、mmap、GIO 异步；但纯 Python 引擎 + GTK3 文本视图，大文件/超大目录性能一般（数万行文件即明显变慢）。

**优点**：架构分层教科书级（引擎纯 Python 无 UI 依赖，可单测）；VCS 适配层设计值得照抄；跨 Win/macOS/Linux。
**缺点**：性能上限低（Python 引擎 + GTK 文本组件）；Windows/macOS 打包一直是痛点；无图片/表格/16 进制之外的比较类型扩展框架。
**可借鉴点**：① matchers 引擎完全独立于 UI；② stat 缓存 + mmap 哈希的目录比较提速套路；③ vc/ 适配器层；④ filediff 内联编辑后**实时重算 diff**（编辑-比较一体是 BC 核心体验）。

### 2.2 KDiff3（Qt / C++）

| 项 | 内容 |
|---|---|
| 仓库 | https://invent.kde.org/sdk/kdiff3 （镜像 https://github.com/KDE/kdiff3 ） |
| 技术栈 | C++ / Qt（5.12+），1.12.x 起提供 Qt6/KF6 构建；依赖 KF Config/XmlGui/**KIOWidgets**/I18n/Crash |
| 许可证 | **GPL-2.0-or-later** |
| 活跃度 | GH 镜像 630 star；最新 1.12.6（2026），2025 年发 1.12.2/1.12.3；提交活跃（几乎每日） |

**模块划分（源码 `src/` 实测）**

| 子模块 | 文件（大小） | 职责 |
|---|---|---|
| diff 核心 | `diff.cpp/.h`（60KB）、`gnudiff_*.cpp`（内嵌 GNU diff 源码） | 行级 diff 引擎 + diff3 合成 |
| 手工对齐 | `ManualDiffHelpList`（diff.cpp 内） | 用户手动指定锚点行，锚点间重新 diff |
| 文本视图 | `difftextwindow.cpp`（76KB）、`Overview.cpp`（差异总览条） | 三窗格同步滚动 + 概览 |
| 合并 | `mergeresultwindow.cpp`（99KB）、`MergeEditLine.cpp`、`merger.cpp` | 三方合并结果编辑器，逐块选 A/B/C |
| 目录比较 | `directorymergewindow.cpp`（**112KB**）、`MergeFileInfos.cpp` | 目录树递归比较与目录级合并 |
| 文件访问 | `fileaccess.cpp`（33KB）、`DefaultFileAccessJobHandler.cpp` | **基于 KIO 的文件访问抽象**（透明支持 fish/sftp/ftp/webdav 等远程协议） |
| 过滤 | `CvsIgnoreList.cpp`、`GitIgnoreList.cpp`、`CompositeIgnoreList.cpp` | 目录比较时按 VCS 忽略规则过滤 |
| 其他 | `progress.cpp`（可取消进度代理）、`Options.cpp`、`CommentParser.cpp`（注释感知选项） | — |

**diff 算法（源码确认）**：
- 行级：`DiffList::runDiff()` 直接调用**内嵌的 GNU diff**（`GnuDiff::diff_2_files`），强制 `IGNORE_ALL_SPACE`，可选忽略数字、可选 minimal（"try hard"）。即 GNU diffutils 的 Myers + 启发式。
- 行内（字符级）：自研有界最优匹配搜索（`DiffList::calcDiff(line1, line2, maxSearchRange)`），并硬性限制 diffList ≤ 50MB 防失控。
- 手工对齐：用户标记锚点后，锚点区间内重新调用 GNU diff——"人工干预 diff"的独家实现。

**三向合并**：自研 diff3 合成——`calcDiff3LineListUsingAB/UsingAC/UsingBC` 把两两 DiffList 编织成 Diff3LineList，再 `calcDiff3LineListTrim()` 去公共前缀/后缀、判定冲突块；冲突内可逐行/逐字符选择来源，支持自动合并 + 基准侧缺失（add/add、delete/modify）处理。

**目录比较**：KIO 递归列举 + 按相对路径配对；支持 2/3 向目录比较与**目录级合并**（整目录选择 A/B/C 拷贝方向）；支持 CVS/Git 忽略规则；后台线程 + `ProgressProxy` 可取消。

**语法高亮**：无完整语法高亮引擎（CMake 依赖中无 KSyntaxHighlighting），仅 CommentParser 感知注释行（用于"忽略注释差异"类选项）。

**优点**：三向合并体验业界口碑最好之一；KIO 抽象让远程目录比较"天然"可用；手工对齐锚点是独门能力。
**缺点**：UI 代码巨石化（单文件 10 万行级 directorymergewindow）；代码高度耦合、现代化重构难；无语法高亮；GNU diff 内嵌带来维护包袱。
**可借鉴点**：① 三窗格 + 概览条 + 同步滚动的信息架构；② KIO 式"文件访问抽象层"思路（在非 KDE 技术栈中对应自建 VFS 接口）；③ 手工对齐锚点功能；④ 目录级三方合并的操作模型。

### 2.3 WinMerge（Windows / C++ / MFC）

| 项 | 内容 |
|---|---|
| 仓库 | https://github.com/WinMerge/winmerge |
| 技术栈 | C++ / **MFC + ATL**（Windows 专用）、GDI+；仅 Windows（社区有 WebDiff 等衍生） |
| 许可证 | **GPL-2.0**（内嵌 GNU diffutils、7-Zip、Frhed 等） |
| 活跃度 | **9,367 star**；2.16.x 每月发版（2.16.50 2025-07、2.16.52 2025-10，当前稳定 2.16.60）；极活跃 |

**模块划分（源码 `Src/` 实测）**

| 子模块 | 文件/目录 | 职责 |
|---|---|---|
| 比较引擎族（策略模式） | `CompareEngines/`：`Wrap_DiffUtils`（包 GNU diffutils）、`FullQuickCompare`（自研整行比较）、`ByteCompare/ByteComparator`（二进制逐字节）、`BinaryCompare`、`ImageCompare`（图片）、`TimeSizeCompare`、`ExistenceCompare` | **按比较方法可插拔**，是所有竞品中最接近"引擎插件化"的 |
| diffutils 内嵌 | `Src/diffutils/`（GNU diffutils） | 行 diff 实际执行者（Myers） |
| 包装层 | `DiffWrapper.cpp`（62KB）、`DiffList.cpp` | 把 GNU diff 的 hunk 转内部块结构 |
| 目录比较 | `DirScan.cpp`（36KB）、`DiffContext.cpp`、`DiffItem*`、`DiffThread.cpp`（后台线程）、`DirTravel.cpp` | 递归扫描 + 配对 + 线程池比较 |
| 目录视图 | `DirView.cpp`（**163KB**）、`DirDoc.cpp`/`DirFrame.cpp`（Doc/View 架构） | 虚拟化列表、按列过滤/排序 |
| 压缩包 | `7zCommon.cpp`、`ArchiveTool.cpp` | **7-Zip 集成**：直接比较 zip/7z/tar 内文件 |
| 16 进制 | 内嵌 **Frhed** 十六进制编辑器 | 二进制差异查看 |
| 过滤器 | `FilterEngine/`、文件名/路径/属性过滤器（.flt + 正则） | 目录比较过滤体系 |
| 其他 | `ColorSchemes.cpp`、shell 集成、`DirCmpReport`（HTML/XML 报告）、补丁生成 | — |

**diff 算法**：行级 = GNU diffutils（Myers + 启发式）；行内 = 自研 token 级高亮；二进制 = 逐字节 + 块级；图片 = 像素级叠加/闪烁比较；另有"快速比较"（不生成完整 diff，只判等）。

**目录比较**：`DiffThread` 后台线程 + 上下文对象；扫描与比较流水线化；支持仅时间/大小快速判定、按扩展名选择比较器；结果可按状态过滤。2.16.50 曾出现"大文件+只显示比较结果模式"崩溃（2.16.50.2 修复）——大文件性能是需要专门设防的证据。

**三向合并**：支持三方文件比较/合并（较 KDiff3 简单）；目录 3 向比较亦有。

**语法高亮**：自研简易关键字高亮（内置常见语言色表），非完整语法引擎。

**优点**：功能覆盖面最接近 BC（文本/文件夹/图片/二进制/16 进制/表格类 CSV 选项、压缩包、过滤、报告）；Windows 下久经考验；引擎族策略模式清晰。
**缺点**：仅 Windows（MFC 绑死）；代码老、单文件巨大；远程协议缺失（靠 UNC/映射盘）；UI 无现代化路径。
**可借鉴点**：① **CompareEngines 策略族 = 比较类型插件化的最佳模板**；② 快速判等（time/size/存在性）与完整比较分层的比较方法矩阵；③ 7-Zip 集成方式；④ 目录比较报告导出。

### 2.5 difftastic（Rust，语法感知 diff）

| 项 | 内容 |
|---|---|
| 仓库 | https://github.com/Wilfred/difftastic |
| 技术栈 | Rust + **tree-sitter**（30+ 语言增量解析）；CLI/终端 UI |
| 许可证 | **MIT**（代码可复用！） |
| 活跃度 | **26,203 star**；持续活跃（作者 Wilfred； crates: tree-sitter/tree-splicer 等） |

**工作原理**：
1. tree-sitter 将两侧解析为语法树（容错、增量）；
2. 节点规范化（合并单孩子链等）后，对树做**基于 Dijkstra 最短路搜索的最小编辑距离树 diff**（自研，非文本算法）；
3. 渲染为带语法上下文的 before/after 面板——**格式化改动（重排空白/换行）不显示为差异**。

**关联**：GumTree（Java，LGPL-3.0，1,341 star）是学术界 AST diff 的代表（细粒度树匹配，用于重构检测），可作为语法感知 diff 的第二条技术路线。

**对新项目的意义**：语法感知 diff 是 BC 没有而现代工具已有的差异化能力。difftastic 是 MIT，其 tree diff 思路可直接借鉴甚至内嵌（作为可选引擎）。注意它是 CLI，无 GUI、无目录比较、无合并（合并支持仍在演进中）。

### 2.7 VS Code 内置 diff / Monaco diff editor

| 项 | 内容 |
|---|---|
| 仓库 | https://github.com/microsoft/vscode 、可复用组件 https://github.com/microsoft/monaco-editor（**46,966 star，MIT**） |
| 技术栈 | TypeScript；Monaco 独立于 VS Code 可单独嵌入任意 Web 应用 |
| 许可证 | MIT（算法代码在 `vs/base/common/diff`，有第三方抽取包 `micnil/vscode-diff`） |

**diff 能力**：
- 1.81（2023-08）起默认启用**新一代 diff 算法**（Henning Dieterichs 主导）：在 Myers 基础上引入锚定与启发式后处理，使 diff 更贴近"开发者实际所做的修改"；1.71+ 支持**代码移动检测**（move detection）。
- 行内词级差异、side-by-side / inline 切换、忽略空白/大小写选项、diff 概览尺。
- **三方合并编辑器**（2022 起）：基线/两侧/结果四区，逐冲突接受与手编——但注意：**merge editor 属于 VS Code 产品代码，并未随 monaco-editor npm 包发布**；Monaco 只带 `createDiffEditor`（2 向）。
- 目录比较：非 Monaco 能力，由 VS Code 资源管理器实现（远弱于 BC/Meld）。

**Monaco 复用性评估**：开箱即得高质量双栏 diff + 同步滚动 + TextMate/Monarch 语法高亮；但官方文档明言 diff editor"为小视图优化"，大文件（数十 MB）有 CPU/内存问题（issue #4801、#5311），频繁创建/销毁 diff editor 有内存泄漏（issue #4659），大量编辑器实例场景需复用 model 与 DOM（vscode#161539）。
**启示**：Web 技术路线做 BC 类工具，**文本 diff 视图可以站在 Monaco/CodeMirror 肩膀上，但大文件与目录树必须自研虚拟化渲染**；VS Code 的新 diff 算法（MIT）是可直接搬的行级算法实现。

### 2.8 git delta（Rust，终端 pager）

| 项 | 内容 |
|---|---|
| 仓库 | https://github.com/dandavison/delta |
| 技术栈 | Rust；**syntect**（Sublime 语法的 Rust 实现）做高亮；自研侧栏对齐引擎 |

## 3. diff / merge 算法专题

### 3.1 行级 diff 算法对比

| 算法 | 原理 | 复杂度 | 输出质量 | 适用场景 | 代表实现 |
|---|---|---|---|---|---|
| **Myers O(ND)** | 在编辑脚本图上对角线搜索最短 D（插入+删除数），中点二分 + 线性空间变体 | 期望 O(N+D)，最坏 O((N+M)·D)；D 大时退化 | 最小编辑脚本，但"错位锚定"会产生违背人直觉的 hunk（大括号配对漂移） | 通用默认；文件间差异小时极快 | GNU diff、git xdiff、Meld myers.py、VS Code（变体） |
| **minimal** | Myers + 更彻底的搜索（不做提前剪枝） | 更慢 | 更小的脚本 | 追求最小补丁 | `git diff --minimal`、GNU diff `-d` |
| **patience** | 只用**两侧均唯一出现**的行做锚点 → 锚点间递归（先做唯一行 LCS） | 接近 Myers，最坏更慢 | 锚点可靠，代码块移动/重排时 diff 显著更符合人眼 | 代码 review、有大括号结构语言 | Bram Cohen 2008；git、Vim/Neovim、imara-diff |
| **histogram** | patience 泛化：按行出现次数分桶，取**低频次行**（不要求唯一）做锚点，递归 | 接近 Myers | patience 的质量 + 接近 Myers 的速度 | 现代默认推荐（学术对比研究认为综合最优） | git 1.8+、JGit、imara-diff、`diffopt=algorithm:histogram` |
| **difflib (SequenceMatcher)** | Ratcliff-Obershelp 风格：递归找最长连续匹配块；带 autojunk（高频行视为垃圾） | O(nm) 级 | 质量尚可；autojunk 对代码（大量重复空行/`}`）常出反效果 | Python 生态、小文件 | Python 标准库（PSF 许可） |
| **GNU diff** | Myers + 上下文启发式（speed/minimal 权衡） | 同 Myers | 与 Myers 相同 | 历史/兼容 unified diff | diffutils（GPL） |

**工程要点**：
- 无论选哪种，标准管线是：**公共前缀/后缀裁剪 → 行内容哈希（把行序列变成整数序列，diff 在哈希上运算）→ 算法本体 → 后处理（相邻 hunk 合并、上下文扩展、移动检测）**。Rust 的 similar/imara-diff 都按此组织。
- 建议新项目实现 **Myers（默认）+ patience/histogram（可选）** 双算法，并提供"忽略空白/大小白/行尾/注释（需语法感知）"预处理钩子——预处理改变输入哈希比改算法容易。
- VS Code 1.81+ 新算法（MIT）值得直接研究移植：锚定 + 后处理让 diff 语义更贴近真实编辑操作，且附带 move 检测。

### 3.2 行内（词级/字符级）diff 实现思路

行级 diff 输出"变更行对"后，对每对行做二次 diff 才能得到 BC 级的行内高亮：

1. **token 化 + 行内 LCS**：把行切成 token（`\w+` 词 + 空白 + 标点），对 token 序列跑小规模 Myers/LCS。delta、多数 GUI 工具用此路；对空白不敏感可选忽略空白 token。
2. **字符级 diff-match-patch**：DMP 以字符为单位，带**超时（deadline）与语义清理**（`semanticCleanup` 合并琐碎编辑、`efficiencyCleanup` 压平抖动）——用于人类可读的行内高亮质量最好，但必须设超时防长行爆炸。
3. **VS Code/Meld 方式**：只对"行级 hunk 中恰好 1:1 配对的行对"做行内 diff（避免 N:M 行对齐歧义），且只对可视区行懒计算。
4. **性能守则**：行内 diff 限定在可见视口内懒计算 + 缓存；单行超过阈值（如 1k 字符）降级为仅行级高亮；超长 hunk 不做行内。

### 3.3 语法感知 diff（tree-sitter 路线）

管线（difftastic 实证）：

```
源码 → tree-sitter 解析（容错、增量） → 节点规范化（解包单链、忽略 trivia）
     → 树 diff（编辑脚本最短路：Dijkstra/A*，节点带语法类型与文本哈希）
     → 映射回行区间 → 渲染（before/after 双栏语法面板）
```

- **优点**：格式化/换行变化不产生噪音差异；能识别"移动的语句"；高亮位置精确到表达式。
- **代价与风险**：每种语言需维护 grammar（tree-sitter 生态已覆盖主流语言，多 MIT）；解析失败需回退行级 diff；结果难以映射为传统 unified patch（与补丁生态兼容性差）；大文件解析内存高于行级。
- 建议定位：**可选增强引擎**（类似 BC 的"格式插件"），默认仍行级 diff，对已知语言类型可切换语法感知。

### 3.4 三向合并（diff3）与冲突判定

**diff3 原理**（GNU diff3 / Khanna–Kunal–Pierce 2007 形式化）：
1. 计算两组双向 diff：base↔ours、base↔theirs；
2. 把变更区间投射到 base 的行坐标上，做**区间配对**：
   - 两组变更区间不重叠 → 各自采纳（自动合并）；
   - 重叠但内容一致（双方做了相同修改）→ 自动合并；
   - 重叠且内容不同 → **冲突块**；
   - base 一侧无对应（add/add、delete/modify）→ 特殊冲突类别；
3. 输出带 `<<<<<<<`/`=======`/`>>>>>>>` 标记的合并文本或结构化冲突列表。

**变体**：
- **zealous diff3（zdiff3）**：冲突块内部再提公共前后缀，缩小冲突范围（git 2.35+ `conflictstyle=zdiff3`）。
- **KDiff3/Meld 的 GUI 合并**：不输出标记文本，而是维护"逐块来源（A/B/C）"的结构化合并模型 + 用户逐块选择——这是 BC 类工具的正确形态。
- 现成实现参考：GNU diff3（GPL）、**node-diff3**（JS，行为对齐 GNU）、Meld `merge.py`（纯 Python 可读性好）、KDiff3 `calcDiff3LineList*`（C++）、Rust `diffy`/`diffy-imara`（MIT，基于 imara-diff）。
- 冲突检测策略要点：区间重叠判定 + 双方内容哈希相等即消解；对"一方删除一方修改"要显式作为冲突类别（而非静默选择）；支持可配置的激进/保守等级。

### 4.5 推荐结论

1. **真正的架构决策不是"选哪个 UI 框架"，而是"引擎与 UI 进程隔离"**：把 diff/merge/扫描引擎做成**无 UI 依赖的 headless Rust 核心**（独立进程，JSON-RPC/IPC 通信，天然支持 CLI 与自动化测试）。做到这一点后，UI 框架选择**可逆**，矩阵中 A/B 分差（4.15 vs 4.10）无足轻重。
2. 在此前提下，**首选 B：Tauri 2 + Web 前端（React/Vue + 自研虚拟滚动 + CodeMirror 6 merge / Monaco 可选）**：引擎与壳同用 Rust（similar + imara-diff + tree-sitter + difftastic 思路全在 Rust 生态），体积/内存最接近 BC 的"工具软件"质感。
3. **保底路径 A：Electron**。若 Linux WebKitGTK 渲染性能或 WebView 差异造成不可接受的成本，Electron 用同一套 Web 前端即可迁移（这正是引擎/UI 解耦的价值）；Monaco 的 diff editor 在该路线下复用度最高。
4. **Qt（C++/PySide6）推荐给"团队本身就是 Qt/C++ 背景"的情形**：模型-视图体系对 10 万行树最从容，但要接受 diff/编辑器组件自研与 GPL 竞品代码不可复用的现实。
5. **纯 Native 双实现不予推荐**：无任何开源先例，成本双倍且无复用红利。

## 6. 对新项目的架构启示

### 6.1 从竞品提炼的共性分层

```
┌───────────────────────────────────────────────┐
│ UI 层：视图族（文本/目录/图片/16 进制/表格/合并） │  ← 每种"比较类型"一个视图组件（Meld 的 *Diff 类族、WinMerge CompareEngines 对应的视图族）
├───────────────────────────────────────────────┤
│ 会话层：会话对象（路径对/三方 + 过滤器 + 选项 + 布局）│  ← BC 的 Session 即一等公民；Meld windowstate/recent、KDiff3 RecentItems 的泛化
├───────────────────────────────────────────────┤
│ 比较编排层：任务调度、进度、取消、增量刷新、结果流 │  ← Meld task.py、KDiff3 ProgressProxy、WinMerge DiffThread
├───────────────────────────────────────────────┤
│ 引擎层：diff/merge 引擎族（文本/树感知/二进制/图片/│  ← 纯算法、无 IO、可单测、可 CLI 化
│          结构化）+ 结果模型（块/冲突结构）        │
├───────────────────────────────────────────────┤
│ VFS 层：本地/远程(rclone sidecar)/压缩包(libarchive)│  ← KDiff3 的 FileAccess、Meld 的 GIO 抽象的非 KDE 泛化
│          统一异步文件接口 + 监听 + 缓存(stat/hash) │
└───────────────────────────────────────────────┘
```

### 6.2 模块边界草案（供下一阶段细化）

1. **引擎进程与 UI 进程硬隔离**（参考 VS Code extension host 模式）：引擎 Rust headless，IPC 走 JSON-RPC（批量、可流式推送目录比较进度）；同一引擎直接产出 CLI（`aic diff a b`）与测试基准。
2. **比较类型 = 插件三元组**（探测器 + 引擎 + 视图）：竞品证据是 WinMerge CompareEngines + Meld 视图类族；新项目应把"内容类型探测 → 引擎选择 → 视图绑定"做成注册表。
3. **VFS 统一异步接口**：`list/stat/read(open→chunk)/watch`，本地直连、远程走 rclone sidecar、压缩包走 libarchive；**所有比较引擎只面对字节流 + 行索引**，不感知来源。
4. **结果模型不可变 + 流式**：目录比较结果以增量消息（发现/状态变更）推送；文本 diff 结果为块区间数组（类似 Meld chunk / KDiff3 DiffList），可被多视图（编辑器、概览条、导航列表）共享。
5. **编辑即重 diff**：filediff 的在编辑体验（Meld/KDiff3/BC 共有）要求引擎支持**局部重算**（imara-diff 的历史化 diff 正是为此设计）。
6. **性能设施先行**：行哈希管线、stat/hash 缓存（Meld CacheResult 模式）、有界并行扫描、全链路取消（KDiff3 ProgressProxy 模式）、虚拟滚动渲染——这五件事是"10 万文件 / GB 文本"目标的地基，须在架构期预留接口而非事后优化。

## 7. 风险与开放问题

### 7.1 风险

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R1 | **GPL 传染**：Meld/KDiff3/WinMerge/libarchive 内嵌 diffutils 均为 GPL，参考实现时"看代码写代码"可能构成衍生作品 | 高 | 只参考行为与文档，不复刻表达；代码复用仅限 MIT/Apache 资产（similar、imara-diff、VS Code diff、difftastic） |
| R2 | **Web 路线大文件渲染**：Monaco 明示小视图优化、社区多次大文件 OOM 报告 | 高 | 文本视图以 CodeMirror/自绘 canvas 为主，Monaco 仅作可选；虚拟滚动 + 视口懒加载行内 diff |
| R3 | **Tauri 三 WebView 差异**（尤其 Linux WebKitGTK 性能） | 中 | 决策矩阵中 Electron 保底；渲染层抽象出可切换 shell；CI 上三平台性能回归测试 |
| R4 | rclone sidecar 分发（约 +40–50MB）与安全面 | 中 | 按需下载/打包可选组件；rc API 仅监听 localhost；或裁剪只编译所需 backend |
| R5 | tree-sitter 各 grammar 许可证不一 | 中 | 建立 grammar 许可证清单入库审查 |
| R6 | unRAR/7z 特别条款（不可用于创建 RAR 压缩等限制） | 低 | 只做解压浏览；合规文案与 NOTICE |
| R7 | 语法感知 diff 与传统补丁生态不兼容（无法生成可 apply 的 patch） | 中 | 定位为增强视图，不进入补丁生成路径 |
| R8 | 性能目标（10 万文件/GB 文本）无竞品实测基线可比 | 中 | 立项初期建立基准集（生成合成目录树与大文件）持续度量 |

### 7.2 开放问题（留待下一阶段）

1. UI 框架最终定夺前的 **PoK（proof of knowledge）验证项**：Tauri/WebView2 下 10 万行目录表滚动帧率；CodeMirror merge 视图三窗格同步滚动实现；Rust 引擎 IPC 吞吐是否支撑 GB 文件行索引流式传输。
2. 引擎语言是否锁定 Rust（矩阵前提）？若团队 Python/TS 为主，需重新评估 PySide6 + Rust 桥 或 Electron + NAPI-RS 组合。
3. 目录比较是否需要**重命名/移动检测**（按内容指纹配对，而非仅路径配对）——所有竞品均未做好，是差异化机会也是算法成本点。
4. 会话同步（跨设备）、脚本化（BC 有强大脚本接口）的范围与形态。
5. 商业模式与许可证选择（决定 R1 的约束强度：若新项目本身开源 GPL，可复用资产池会显著扩大）。
